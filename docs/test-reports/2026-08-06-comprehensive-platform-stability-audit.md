本轮以公网真实用户路径为主线，完成了超级管理员、平台管理员、科研用户、普通用户和游客五类身份的登录、页面、权限、资源、地图、分析、成果、后台及异常登录验证，并用本地全量自动化门禁补充验证高风险写操作和组件逻辑。

仍需持续观察或由运维/产品确认的事项包括：公网仍使用 HTTP、平台管理员测试账号叠加科研用户角色、游客公开原始数据为 0、栅格瓦片并发读取存在约 8.17 秒尾延迟，以及历史格式化基线债务。这些项目当前均未造成已验证业务流程失败，但不应从发布风险清单中删除。

## 3. 测试策略与判定规则

### 3.1 角色驱动的端到端检查

每个角色均从真实登录/游客入口开始，按该身份实际可见导航逐页检查，并额外直接访问兼容路由和受限路由，确认允许功能可用、禁止功能被稳定阻断。平台管理员账号实际同时属于“平台管理员”和“科研用户”，本轮按服务器返回的真实权限并集验证，并单独记录角色纯度风险。

### 3.2 页面稳定性检查

对页面检查以下条件：最终路由正确、主内容非空、无整页横向溢出、无未处理脚本异常、无失败请求、无业务 4xx/5xx、权限重定向符合预期。对数据目录、地图、非地理分析、成果预览、动态机构详情和后台用户管理执行了进一步真实交互或内容检查。

### 3.3 服务与并发稳定性检查

通过五个已登录/游客会话并发读取核心 API，并对同一真实栅格瓦片执行并发一致性读取。该测试关注 HTTP 状态、内容一致性、典型延迟和尾延迟，不执行压力破坏、写入竞争或容量极限测试。

### 3.4 本地发布门禁

运行后端测试、前端单元测试、Chromium 浏览器组件测试、品牌检查、OpenAPI 合同与生成客户端一致性检查、TypeScript、Ruff 规则检查和 Vite 生产构建。格式化检查作为基线债务单列，不对历史文件做大面积改写。

## 7. 公网网络与并发结果

### 7.1 五会话核心 API 并发读取

每个会话对以下接口各执行 40 次组合读取，共 5 会话 × 40 = 200 次请求：

- `/api/health/`
- `/api/auth/me/`
- `/api/catalog/resources/`
- `/api/catalog/map-compositions/`
- `/api/catalog/results/`

结果：200/200 为 HTTP 200，无失败。各会话 p50 约 74–101 ms；超级管理员冷启动尾延迟最高约 2.0 秒，随后恢复正常。

### 7.2 真实栅格瓦片并发一致性

4 个拥有栅格访问权的身份各并发读取 10 次，共 40 次。结果为 40/40 HTTP 200，每次响应均为 74,273 bytes，内容长度一致；最大尾延迟约 8.17 秒。功能和内容一致性通过，但尾延迟显著高于核心 API，应在生产监控中持续记录 p95/p99、并发连接和缓存命中率。

### 7.3 控制台与协议观察

- 已认证业务接口无业务 4xx/5xx。
- 登录前 `/api/auth/me/` 的 401 属于预期会话探测。
- 公网为 HTTP，浏览器因此忽略 `Cross-Origin-Opener-Policy` 响应头并记录控制台错误。当前测试流程未受影响，但正式生产应迁移 HTTPS 后复核 COOP/COEP/CSP 等安全响应头。
- CLI 输出中的中文乱码来自 Windows Conda/GBK 输出转码，真实浏览器截图中的中文显示正常，不是前端乱码缺陷。

## 9. 发现项、处置与风险分级

### P1 / 发布阻断

本轮未发现 P1 或必须立即修改代码的发布阻断缺陷。

### P2 / 发布后需治理或持续观察

1. **公网 HTTP 与安全响应头失效**：COOP 在不可信 HTTP Origin 上被浏览器忽略。建议配置域名、TLS 证书和 HTTPS 网关后复核安全头；该事项涉及基础设施，本轮不擅自修改。
2. **平台管理员账号角色叠加**：测试账号同时属于平台管理员和科研用户，权限为并集。建议准备只属于单一平台管理员角色的长期验收账号。
3. **游客公开原始资源为 0**：页面空态和权限行为正确，但如果产品目标包含游客浏览原始数据，需要管理员选择资源并配置公开范围。
4. **栅格瓦片尾延迟**：40 次一致性读取全部成功，但最大约 8.17 秒。建议建立至少 7 天 p95/p99 监控，结合磁盘 IO、缓存和并发连接定位是否需要容量优化。

### P3 / 工程基线债务

1. OpenAPI 校验存在 6 条未使用组件警告，不影响合同有效性或客户端一致性。
2. `pnpm run check` 的格式阶段报告 171 个文件，包含大量历史 `.playwright-cli` 产物；`ruff format --check` 报告 51 个历史文件需格式化。规则检查、类型检查、测试和构建均通过。本轮没有批量格式化，以免扩大变更面或覆盖用户产物。
3. 公网启动信息没有返回构建提交指纹。建议在只读健康或版本接口中提供版本号、提交 SHA 和构建时间，便于把公网行为证据精确绑定到发布制品。

### 本轮代码处置

本轮没有发现需要修复的新功能缺陷，因此未修改应用代码或 API 合同。对于 HTTP、角色纯度、公开数据策略和性能监控等需要基础设施或产品决策的事项，只记录建议，不在未确认的情况下进行底层或生产配置改动。

## 10. 发布判断与后续建议

当前版本通过五角色公网真实浏览器回归、关键交互、权限阻断、200 次核心 API 并发读取、40 次真实瓦片一致性读取及本地全量自动化门禁，可作为 **V3.20 稳定发布候选版本**。这表示本轮覆盖内没有发现阻断发布的问题，不等同于对所有未知负载、浏览器组合和长期运行状态作绝对无缺陷承诺。

建议发布流程继续保留以下门禁：

1. 发布制品固定到明确提交 SHA/镜像 digest，并在健康接口暴露可核验版本指纹。
2. 部署前保留数据库、配置和上一镜像的可恢复快照；部署后复核健康、启动配置、容器重启/OOM 状态和关键五角色冒烟流程。
3. 为纯平台管理员建立独立验收账号，并明确游客公开原始资源策略。
4. 启用 HTTPS，并复核 COOP/COEP/CSP、安全 Cookie 和反向代理头。
5. 对核心 API、栅格瓦片、外部底图分别建立 p50/p95/p99、错误率和超时率监控；优先观察栅格瓦片尾延迟。
6. 将格式化债务安排为独立维护任务，排除运行产物后分批处理，不与稳定性功能修复混在同一发布中。
